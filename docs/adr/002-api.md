## Estado

**Aceptado** el 22 de noviembre de 2026.

Esta decisión se aplica a todo componente nuevo y a todo cambio en las props de uno existente. Los componentes que hoy no la cumplen se adaptan en PR aparte. Para cambiarla, se escribe un ADR nuevo que la sustituya; este archivo no se edita para cambiar lo decidido.

## Contexto

La API de un componente son los nombres con los que se usa: sus props y los valores de esas props. Es lo que escribe cada persona y cada agente de IA en cada pantalla.

El ADR-001 fijó tres props de aspecto (`variant`, `tone` y `size`), pero no el resto del vocabulario. Sin una lista completa, cada pieza ha nombrado lo mismo a su manera:

- **El aspecto**, con dos palabras: `variant` en Button y `tone` en Badge.
- **El error de un campo**, con una prop `error` que es a la vez un texto y un sí/no.
- **La posición del icono**, con dos props (`icon` + `iconPosition`) en Button y una sola (`icon`) en el resto.

Cada nombre propio es una regla más que hay que aprender. Y en solaris-ds buena parte del código la escriben agentes: si el nombre no es el que el agente espera, se lo inventa, y la API se fragmenta.

[`docs/prop-map.md`](../prop-map.md) recoge el vocabulario completo, los valores y las excepciones. Este ADR lo convierte en norma.

## Decisión

### 1. El mapa de props es la norma

Toda prop y todo valor de un componente de solaris-ds usa el nombre **Correcto** de [`docs/prop-map.md`](../prop-map.md). Los nombres de la columna **Prohibido** no se usan nunca, ni como alias.

| Para qué | Nombre |
|---|---|
| Aspecto según el significado | `variant` (también en Badge: `tone` desaparece) |
| Tamaño | `size`: `sm`, `md`, `lg` |
| Estados que decide quien usa el componente | `disabled`, `invalid`, `isLoading` |
| Texto de error de un campo | `errorMessage` |
| Eventos | `onClick`, `onSubmit`, `onChange` |
| Nombre visible de un campo | `label` |
| Contenido | `children` |
| Iconos | `iconStart` (delante del texto) e `iconEnd` (detrás) |

**Valores de `variant`:**

- **Acciones:** `primary`, `secondary`, `ghost`, `danger`.
- **Estados:** `neutral`, `info`, `success`, `warning`, `danger`.
- Cada componente ofrece solo los valores que necesita, siempre de estas dos listas.
- El valor nombra el **significado**, nunca el color (`danger`, no `red`), y va en inglés.
- **`danger` y nunca `error`**, ni `destructive` ni `critical`. La palabra `error` solo aparece en `errorMessage`.

Con esto, el principio 3 del ADR-001 queda así: **solo dos props cambian el aspecto de un componente, `variant` y `size`**, con los valores de arriba. Y el principio 5a: **todo `variant` de estado lleva texto**, y el componente no se puede usar sin él.

### 2. Se elige siempre el nombre que un agente usaría por defecto

Cuando haya que elegir entre dos nombres, gana el que un agente de IA escribiría **sin haber leído nada del sistema**: el más repetido en React, en HTML y en los design systems públicos.

Por qué:

- **Acierta a la primera.** Un agente (Claude, Dust…) genera la mayor parte del código. Si el nombre coincide con lo que ya espera, no hay que enseñárselo ni corregirlo.
- **Las personas tampoco tienen que aprender nada.** Quien ha trabajado con React reconoce `onClick`, `disabled` o `size` sin leer documentación.
- **Menos reglas que vigilar.** Cada nombre propio es una excepción que alguien tiene que recordar en cada PR.

Solo hay una razón para apartarse del nombre por defecto: que sea un atributo de HTML con otro significado (ver punto 3) o que rompa una regla de accesibilidad o de salud. En ese caso, se escribe el motivo en la columna **Notas** del mapa.

Ejemplos de cómo se aplica: `iconStart` y no `iconLeft`, porque "delante" no siempre es la izquierda; `disabled` sin `is` porque es el atributo de HTML; `isLoading` con `is` porque HTML no lo tiene.

### 3. Los atributos de HTML no se renombran

Si HTML ya tiene un nombre para algo, el componente lo acepta **con ese nombre y ese significado**, y lo pasa al elemento de HTML:

- **Formularios:** `type`, `name`, `value`, `defaultValue`, `placeholder`, `required`, `readOnly`, `autoComplete`, `inputMode`, `disabled`.
- **Eventos:** `onClick`, `onChange`, `onSubmit` y el resto de `on…`.
- **Identidad y estilo:** `id`, `htmlFor`, `className`, `style`, `title`.
- **Accesibilidad:** `aria-*`, `role`, `tabIndex`.
- **Enlaces:** `href`, `target`, `rel`.

Consecuencias de esta regla:

- **Un nombre de HTML no se usa para otra cosa.** `type` es el tipo de HTML (`button`, `submit`), nunca el estilo: para el estilo está `variant`.
- **Excepción: `title` en los componentes con encabezado visible** (como Card). Es el nombre que usa cualquier agente para el título de una tarjeta o de un diálogo, así que se mantiene: en esos componentes, `title` es el texto del encabezado y no el tooltip de HTML.

### 4. Figma usa los mismos nombres

Las propiedades de los componentes en Figma se llaman igual que las props de código. Un icono que se puede quitar lleva dos propiedades:

- **`iconStart`**: cambio de instancia, para elegir el icono.
- **`iconStart.`**: booleana con el mismo nombre y un punto al final, para mostrarlo u ocultarlo. Figma no deja repetir nombre y el punto deja claro que las dos son la misma prop de código.

Igual con `iconEnd` e `iconEnd.`.

### 5. Quién decide un nombre nuevo

- **Quién propone:** cualquier persona o agente, con una PR que añade la fila a `docs/prop-map.md` (Correcto, Prohibido y Notas). Antes, comprueba que no existe ya un nombre en el mapa para lo mismo.
- **Cómo se elige:** con la regla del punto 2. La PR explica por qué es el nombre que un agente usaría por defecto, y qué sinónimos quedan prohibidos.
- **Quién aprueba:** **lago-gif**, igual que cualquier componente nuevo (ADR-001, Gobierno).
- **Cuándo hace falta un ADR nuevo:** para cambiar o quitar un nombre que ya está en el mapa, o para cambiar las reglas de este ADR. Añadir un nombre nuevo que las cumple solo necesita la PR al mapa.
- **Un agente no inventa nombres.** Si una tarea necesita una prop que no está en el mapa, la propone en la PR y la señala; no la usa como si ya existiera.

## Consecuencias

### Lo que ganamos

- **Un solo vocabulario** para todos los componentes, en código y en Figma.
- **Agentes más fiables:** escriben la API correcta sin leer cada componente, porque los nombres son los que ya conocen.
- **Comprobable en cada PR:** basta con buscar los nombres de la columna Prohibido en `src/components/`. Resultado esperado: 0.
- **Menos dudas al crear componentes:** el nombre de casi cualquier prop ya está decidido.

### Lo que cuesta

- **Hay que renombrar props existentes** (`tone`, `error`, `icon`, `iconPosition`) y actualizar sus historias, contratos y usos. Es un cambio que rompe el código que ya los use.
- **Mantener el mapa:** cada prop nueva pasa por `docs/prop-map.md` antes de usarse.

### Lo que no cambia

- **Los nombres de los tokens:** el rol de color sigue siendo `danger` y los tokens no se renombran.
- **El resto del ADR-001:** alcance, tokens, gobierno y los principios 1, 2 y 4 siguen igual.
- **La rama `antes` y `src/screens/antes.tsx`** siguen congeladas como ejemplo.
